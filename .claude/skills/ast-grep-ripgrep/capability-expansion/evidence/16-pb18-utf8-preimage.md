# Evidence 16 — PB18: a string prefix preimage is constructible, and it fires

§10.1's UDF inventory marks three of twelve functions as implementing `preimage`, and one of
them — `entity_key_namespace(key)` — is the only string-valued one. PB06 established that the
mechanism works, but every arm it measured was `Int64`. Whether `Interval` accepts `Utf8` bounds
at all is stated nowhere in the pinned API surface.

| | |
|---|---|
| Question | Can a `preimage` express a **string prefix** range, and does it prune a Delta scan? |
| Verdict | **CONFIRMED** — `Interval::try_new(Utf8, Utf8)` constructs, the rewrite fires, and it reaches the same range a hand-written predicate produces |
| Closes | §10.1's "`entity_key_namespace(key)` … **yes** — prefix range", which was a design claim with nothing behind it |

- Source: [`probes/delta-arrow-probe/examples/pb18_utf8_preimage.rs`](probes/delta-arrow-probe/examples/pb18_utf8_preimage.rs)
- Capture: [`probes/PB18-utf8-preimage.out.txt`](probes/PB18-utf8-preimage.out.txt)

---

## What ran

Four files, one namespace each, written as four separate appends so every file carries its own
min/max statistics — PB06's shape, because pruning has to be observable as *files* rather than
inferred from plan text.

```
  Q1  Interval::try_new(Utf8, Utf8)   OK    Interval { lower: Utf8("mech:"), upper: Utf8("mech;") }

  A  preimage UDF         rows= 50  rewritten_to_range=true
      Filter: keys.entity_key >= Utf8View("mech:") AND keys.entity_key < Utf8View("mech;")
  B  CONTROL no preimage  rows= 50  rewritten_to_range=false
      Filter: entity_namespace_np(CAST(keys.entity_key AS Utf8)) = Utf8("mech")
  C  GOLD hand-written    rows= 50  rewritten_to_range=true
      Filter: keys.entity_key >= Utf8View("mech:") AND keys.entity_key < Utf8View("mech;")
```

**Arm A reaches arm C exactly.** The rewritten predicate is not merely *a* range, it is the same
range a person would have written, which is the ceiling this mechanism can reach.

**Arm B is the control and it is load-bearing.** It is the same UDF, the same volatility, the same
signature, differing only in returning `PreimageResult::None`. It does not rewrite. Without it,
arm A's rewrite could have been any of the optimizer's ordinary simplifications rather than the
preimage, and PB06's own first reading is the reason not to assume: `get_preimage` returns `None`
unless the left side is a `ScalarFunction`, the right side is a literal, **and** the volatility is
`Immutable` — and a `Volatile` UDF is skipped with no diagnostic at all.

All three arms return the same 50 rows, which is what makes them one question rather than three.

---

## What this settles for the implementation

1. **`entity_key_namespace` can carry a `preimage`**, half-open, over the bare stored column —
   `['<ns>:', '<ns>;')`, since `;` is `:` plus one in ASCII, so the range holds every key in the
   namespace and nothing else.
2. **§10.2's two `preimage` checks come into force with it.** They have had nothing to check until
   now: the bucket-boundary test (a closed upper bound is off by exactly one row, and invisible
   without a case that sits on the boundary) and the bare-stored-column rule (a derived expression
   rewrites but cannot prune, because Delta's statistics are keyed on stored columns).
3. **The rewritten literal comes back as `Utf8View`, not `Utf8`.** Consistent with PB05's
   `schema_force_view_types` finding, and harmless here because the comparison is generated by the
   optimizer rather than written by this code — but it is the third place that coercion has
   surfaced, and the first where it did no damage.

## What it does not settle

Whether the rewrite **prunes files** rather than merely rewriting. All four files were read in
each arm: with 200 rows across four files and a 50-row answer, the row counts are identical
whether pruning happened or not, because `Filter` removes the rest either way. PB06 measured
pruning directly for the `Int64` case by counting files; doing the same here needs the file-count
channel that probe used, and this probe did not ask for it.

That is a gap and not a blocker: the design's requirement is that the predicate reaches the scan
as a range over a stored column, which is what was measured. If a string-keyed filter ever becomes
hot, the file-count arm is the next thing to add.
